## Doc changes
- `docs/API.md`, Auth:
  - `POST /api/auth/register` → 201 `{ email }` (code sent; no session). 409 `already_registered`; 503 if the project has confirmations off.
  - `POST /api/auth/verify-email` `{ email, token }` → session. `POST /api/auth/resend-code` `{ email }` → 204.
  - `POST /api/auth/forgot-password` `{ email }` → 204. `POST /api/auth/reset-password` `{ email, token, password }` → 204, ends every session.
  - `POST /api/auth/refresh` `{ refresh_token }` → session; any failure 401.
  - `GET /api/auth/me` → full account incl. `residency_status`, `residency_note`, `has_residency_proof`.
  - `POST /api/auth/me/residency-proof` (citizen, multipart `proof`, JPG/PNG/WebP/PDF ≤ 5 MB) → `{ user }`.
  - Lock: citizen routes answer 403 `{ details: { code: "residency_required" } }`.
- `docs/API.md`, Admin: `GET /api/admin/users?residency=pending|verified|rejected`; `GET /api/admin/users/:id/residency-proof` → `{ url, kind, expires_in: 300 }`; `PATCH /api/admin/users/:id/residency` `{ decision, note? }`; `PATCH /api/admin/users/:id/phone-verified` `{ verified }`.

## Judgment calls and limitations
- `verifyOtp` type `signup`, not `email` (Supabase's `email` also accepts reset codes).
- Profile is built from sign-up metadata on the first confirmed session; Supabase keeps the first details of an unconfirmed address, so a re-registration only resends the code.
- Proof upload is signed in: before the email code nothing proves whose account a file belongs to.
- Refresh token in localStorage (user's choice); an httpOnly cookie is the hardening step.
- Reviewer embed uses the column (`reviewer:residency_reviewed_by(...)`): the constraint-name form failed on a real database (bug found in the local run, fixed).
- Minor enumeration: a second code request inside Supabase's per-address window answers 429 only for real addresses.
- If Supabase refuses a new password after the reset code is spent, the person asks for a new code.
- Logout after the access token expires cannot revoke on the server.
